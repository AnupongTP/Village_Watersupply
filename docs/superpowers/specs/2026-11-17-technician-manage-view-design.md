# หน้าช่าง: หน้าจัดการข้อมูลในธีม Reference — Design

วันที่: 2026-11-17 · สถานะ: รอเจ้าของงานอนุมัติ · ยังไม่ commit (เจ้าของงานยังไม่สั่ง)

## เจตนาและเหตุผล

ผู้ดูแลระบบและช่างอำเภอเข้าหน้าช่าง (`/technician/`) เพื่อ **แก้ข้อมูลระบบประปาหลังลงพื้นที่** เป็นหลัก หาระบบด้วยคำค้น
(ชื่อหมู่บ้าน ชื่อประปา หรือคำใดก็ได้ที่เกี่ยวกับจุดนั้น) ใช้ทั้งมือถือและคอม (คำตอบเจ้าของงาน)

หลังย้าย UI ใหม่ (Reference ตาม `index_watersupply (2).html`) หน้าช่างยังมีชิ้นส่วนดีไซน์เดิมโผล่เป็นช่วง ๆ และทางไปถึงปุ่มแก้ไขยาว
(แถว → dialog → แก้ไข หรือ เมนู ⋮ → แก้ไข) เป้าหมายคือทั้งหน้าเป็นระบบเดียวกัน และ "ค้นคำ → แก้ไข" สั้นที่สุด

## เป้าหมาย

1. ปุ่มที่ 3 **"🛠️ จัดการข้อมูล"** ใน `.main-nav` ของ header Reference (ต่อจาก บทสรุปผู้บริหาร / รายละเอียดข้อมูล) เปิด view `#view-manage`
2. ใน view นี้มีแท็บ: **รายการระบบ** | **ประวัติการแก้ไข** | **บัญชีช่างเทคนิค** (แท็บสุดท้ายเฉพาะผู้มีสิทธิ์ `MANAGE_TECHNICIANS`) — header Reference คงอยู่ตลอด ไม่สลับไป header เก่า
3. แท็บรายการระบบ: ช่องค้นหาอยู่บนสุด, ปุ่มกรอง ทั้งหมด/เฝ้าระวัง (ของเดิม), แต่ละแถวมีปุ่ม **"แก้ไข"** เห็นชัด + ปุ่ม **⋯** (ดูประวัติ · ดูบนแผนที่ · ลบ)
4. มือถือ: แต่ละระบบเป็นการ์ด ปุ่มแก้ไขกว้างเต็มการ์ด
5. งานเล็กที่ทำร่วม: หน้าโหลดตอนรีเฟรช (`#bootView`) เป็นธีมม่วง; ป้าย scope อ่านออก; ขอบช่อง login แดงเมื่อไม่ครบ (แก้ regression จากธีม login); ชื่อ **KwanKukkeb** แทน KwanKakKeb ในหน้าเว็บ

## ไม่ใช่เป้าหมาย / ห้ามทำ

- ไม่เพิ่มความสามารถใหม่ ไม่เปลี่ยน dialog แก้ไข/ลบ, การบันทึก, expectedVersion, การจัดการบัญชี — ใช้ของเดิมใน `technician.js`
- ไม่แตะ Backend, Auth, สิทธิ์อำเภอ, กฎเผยแพร่ R5.1, SQL; สิทธิ์ยังมาจาก backend (`UPDATE_SYSTEM`, `DELETE_SYSTEM`, `MANAGE_TECHNICIANS`)
- ไม่เปลี่ยนหน้า บทสรุปผู้บริหาร / รายละเอียดข้อมูล (ต้องเหมือนหน้าสาธารณะตาม Reference)
- ไม่แตะไฟล์ GAS `header.html` ในโฟลเดอร์งานอื่น (งาน KebNamComplete แยก)
- Anti-goal: ช่างเห็นระบบนอกอำเภอ, ปุ่มลบ/แก้ไขโผล่โดยไม่มีสิทธิ์, ออกจากระบบแล้ว DOM/ข้อมูลผู้ใช้ก่อนค้าง

## ข้อจำกัด

- แก้ใน Candidate (`output/reference-ux-candidate/`) + generators (`output/ui-ux-preview/execution/build-reference-*.py`) + `technician/assets/reference-technician.js` (เขียนมือ) แล้วจึงซิงก์ไป root หลัง test ผ่าน
- generator หน้าช่างต้องอ่านต้นฉบับจาก `output/ui-ux-preview/promotion-backup-2026-11-17/root-before/` เพราะ root ถูกแทนด้วยไฟล์ที่แปลงแล้ว
- Node ในเครื่อง v24.15.0 (CI ใช้ 22); ห้ามเรียก API จริง; ไม่ commit/push/deploy จนกว่าสั่ง
- `output/` ถูก gitignore (อยู่ในเครื่องเท่านั้น) — Candidate คือ source ของงาน UI; root เป็นปลายทางซิงก์ (คัดลอกไฟล์ที่ตรงกับ Candidate ทุก byte หลัง test ผ่าน และสำรองไฟล์ root ก่อนทับ)
- `technician.js` ใน root มี working changes เรื่อง password-policy; Candidate สร้างจากฉบับ backup `root-before` ซึ่งมี working changes นั้นอยู่แล้ว — ห้ามทำให้หาย
- `ownsWorkspace()` ยังไม่มีใน `technician.js` ต้นฉบับ: เป็นฟังก์ชันของ bridge (`window.VWSReferenceTechnician.ownsWorkspace`) ที่ต้นแบบทำแล้ว ส่วน `technician.js` patch แค่จุด toggle `#dashboardWorkspace` ให้ถามผ่าน optional chaining

## Approaches ที่พิจารณา

| ทาง | สรุป | ข้อแลก |
|---|---|---|
| **ก (เลือก)** | view จัดการใหม่ใต้ header Reference, ย้าย section เดิมเข้าแท็บ, ปรับหน้าตาแถวให้ปุ่มแก้ไขเห็นชัด | ตรงงานจริงที่สุด, หน้าเป็นระบบเดียว; ต้องเขียน test เดิม ~30 เคสใหม่ |
| ข | คงหน้าแยกเดิม เปลี่ยนแค่ header เก่าเป็นม่วง | test แทบไม่แก้; ยังสลับหน้า, แก้ไขยังซ่อนใน ⋮ |
| ค | เพิ่มปุ่มแก้ไขในตารางรายละเอียดข้อมูล | งานน้อยสุด; ตารางกว้างใช้มือถือยาก, ไม่มีที่ให้ประวัติ/บัญชี |

เจ้าของงานเลือก **ก** หลังดูโครง (wireframe) แล้วตอบ "โอเค"

## สิ่งที่ตัดสินแล้ว (ตามที่เจ้าของงานเห็นในโครง)

- ลำดับแท็บ: รายการระบบ → ประวัติการแก้ไข → บัญชีช่างเทคนิค; บัญชีช่างซ่อนเมื่อไม่มีสิทธิ์
- ประวัติการแก้ไข: ทั้งผู้ดูแลและช่างใช้ได้; บัญชีช่าง: ผู้ดูแลเท่านั้น
- แถวรายการ: ชื่อระบบ + รหัส, หมู่บ้าน/ม./อปท./อำเภอ, ป้ายสถานะ, [แก้ไข] [⋯]
- ⋯ → "ดูประวัติ" สลับไปแท็บประวัติและกรอกรหัสระบบให้ (พฤติกรรมเดิม แต่ไม่ออกจาก header Reference)
- หน้าโหลดตอนรีเฟรช: header ม่วง + ตัวหมุน "กำลังโหลดข้อมูล..." (ตรรกะตรวจ session เดิม)
- dialog แก้ไข/ลบ: ขั้นตอนเดิม ปรับเฉพาะสีให้เข้าธีม

## การตัดสินใจของผู้ออกแบบ (Claude) — เจ้าของงานตรวจได้

1. **ปุ่ม "แก้ไข"**: บัญชีไม่มีสิทธิ์ `UPDATE_SYSTEM` → ไม่แสดงปุ่ม; มีสิทธิ์แต่ระบบ `managementMutable!==true` → แสดงป้ายเล็ก "แก้ไขไม่ได้: ข้อมูลต้นทางมีปัญหา" แทนปุ่ม (ตัวกันพลาด — ผลนับจากฐานข้อมูลจริงที่เจ้าของงานรัน 2026-11-17: 733 ระบบ `NO_RAW_LINK` + 3 ระบบ `RAW_PROCESSED` = แก้ได้ทั้ง 736 ระบบ ไม่มีระบบติดล็อก จึงไม่ต้องแก้ backend และไม่ลงแรงออกแบบป้ายเพิ่ม); ในเมนู ⋯ คงพฤติกรรมเดิม (คำสั่งที่ใช้ไม่ได้เป็น disabled)
2. **ซ่อนแถบตัวกรองใหญ่ (`.gf`) ใน view จัดการ** เพราะไม่มีผลกับรายการ (รายการใช้ช่องค้นหาของตัวเอง) — เลี่ยงความเข้าใจผิด
3. **ลิงก์ hash เดิม** `#technicianManagementSection` → แท็บรายการ, `#watchlist` → แท็บรายการโหมดเฝ้าระวัง, `#historyPanel` / `#techniciansPanel` → แท็บนั้น (บัญชีช่างไม่มีสิทธิ์ → กลับภาพรวมตามเดิม)
4. ปุ่ม "บัญชีช่างเทคนิค" ในเมนูผู้ใช้ซ่อน (ย้ายไปเป็นแท็บ); เมนูผู้ใช้เหลือ เปลี่ยนรหัสผ่าน / ออกจากระบบ
5. ปุ่ม "กลับแดชบอร์ด" ของหน้าแยกเดิมซ่อนใน view จัดการ (header Reference มีปุ่มนำทางอยู่แล้ว)
6. สีตาราง/การ์ดรายการ, ปุ่ม, แท็บ ใช้โทนม่วง Reference (`#5b3fd6`/`#7c5cf0`, เส้น `#e4e0fb`) ข้อความผ่าน WCAG AA
7. **การค้นหาคงเดิม** (`searchableText()` ใน `technician.js`: รหัสระบบ, ชื่อระบบ, หน่วยงานรับผิดชอบ/ให้บริการ, ชื่อหมู่บ้าน, อำเภอ, ตำบล, อปท.) ครอบคลุมตัวอย่างของเจ้าของงานแล้ว จึงไม่ขยายฟิลด์ (ไม่เพิ่มความสามารถ) — ถ้าภายหลังพบคำที่หาไม่เจอ ค่อยเพิ่มเป็นงานแยก
8. **ชื่อ KwanKukkeb**: เปลี่ยนทุกข้อความที่แสดงในหน้าเว็บ Candidate/root รวม `<title>` และ h1 และ test ที่ตรวจข้อความนี้ (`error-empty.spec.js`); ไม่แก้เอกสารประวัติ/รายงานเก่าและไฟล์ GAS

## โครงสร้างการทำงาน (ระดับออกแบบ)

- **markup** (generator หน้าช่าง): เพิ่มปุ่ม `data-view="manage"` และ `#view-manage` (แท็บ + slot) ใน body Reference ที่ฉีดเข้า `#referenceDashboard`
- **bridge** (`reference-technician.js`): หลัง mount ย้าย `#watchlist`, `#historyPanel`, `#techniciansPanel` เข้า view; ประกาศ `ownsWorkspace()` ให้ `technician.js` ไม่ซ่อน `#dashboardWorkspace` เมื่อเปิดประวัติ/บัญชี; sync แท็บตาม workspace/hash; ซ่อนแท็บบัญชีตามสิทธิ์; logout คืน section กลับที่เดิมก่อนรีเซ็ต template
- **technician.js** (patch ผ่าน generator เท่าที่จำเป็น): จุด toggle `#dashboardWorkspace`; renderer แถว (`systemRowHtml`) เพิ่มปุ่มแก้ไขตามข้อ 1
- **CSS** (generator `reference-technician.css`): view จัดการ, แถว/การ์ด, ป้าย scope, `#bootView`, login invalid (`#loginForm input[aria-invalid="true"]` ต้องชนะสีขอบธีม)

ต้นแบบที่ทำไปแล้วใน Candidate (ปุ่ม + แท็บ + ย้าย section + ป้าย scope + ซ่อน `.gf`) ใช้เป็นจุดเริ่มได้ แต่ยังไม่มีปุ่มแก้ไขในแถว, ธีมตาราง, `#bootView`, และทำให้ test เดิมไม่ผ่าน

## การทดสอบ / เกณฑ์รับ

- test ใหม่ `CANDIDATE-UX-09*` (มีแล้ว) + เพิ่ม: ปุ่มแก้ไขในแถวเปิด dialog แก้ไข; ไม่มีสิทธิ์ → ไม่มีปุ่มแก้ไข; ⋯ ดูประวัติ → แท็บประวัติกรอกรหัส; `#bootView` ธีมใหม่; login invalid ขอบแดง; ชื่อ KwanKukkeb
- test เดิมที่ไม่ผ่าน (~30 เคส ส่วนใหญ่ `technician-mock.spec.js`, บางส่วน `reference-ux-isolated` / `reference-review-regressions`): แยกทีละเคสเป็น (a) test ผูกกับพฤติกรรมเดิมที่เปลี่ยนตามการออกแบบนี้ → ปรับ test ให้ตรวจพฤติกรรมเทียบเท่าใหม่โดยไม่ลดความเข้มงวด (สิทธิ์, scroll, focus, ไม่ยิง API ซ้ำ) หรือ (b) บั๊กจริง → แก้โค้ด; บันทึกการตัดสินแต่ละเคส
- baseline ของเคสที่ไม่ผ่าน: รันเต็มชุดใหม่หนึ่งรอบกับต้นแบบก่อนเริ่ม (log รอบก่อน `output/ui-ux-preview/gemini-review/seven-fixes/ux09-e2e-suite.log` ถูกหยุดกลางทาง จึงใช้เป็นรายการตั้งต้นได้แต่ไม่ครบ)
- project `chromium-desktop` รวม describe ขนาดมือถือ/แท็บเล็ต (390/768px) ใน spec อยู่แล้ว จึงเป็น gate ของการ์ดมือถือด้วย; เพิ่ม test การ์ดมือถือปุ่มแก้ไขที่ 390px
- เกณฑ์: E2E chromium-desktop ผ่านทั้งหมด (ยกเว้น real-api skip), Unit/static QA ผ่าน, axe ผ่าน — ทั้งบน Candidate และหลังซิงก์ root
